# APL1000: Do not use the factory-backed UIButton constructor when subclassing

`UIButton(UIButtonType)` is valid when constructing a `UIButton` directly, but not
when calling it as a base constructor from a subclass.

This constructor calls the native `buttonWithType:` factory on `UIButton` and wraps
the returned object. It does not initialize a native instance of your managed
subclass, so native calls will not dispatch to your managed overrides as expected.

For example, the following constructor produces warning APL1000:

```csharp
class FocusableButton : UIButton {
    public FocusableButton () : base (UIButtonType.System)
    {
    }

    public override bool CanBecomeFocused => true;
}
```

Use the default constructor, or another supported initializer, when subclassing:

```csharp
class FocusableButton : UIButton {
    public FocusableButton () : base ()
    {
    }

    public override bool CanBecomeFocused => true;
}
```

Changing the constructor can change the button's appearance or behavior. Review
your styling and configuration rather than treating this as a mechanical
replacement.

If you do not need a subclass, both `new UIButton(UIButtonType.System)` and
`UIButton.FromType(UIButtonType.System)` remain valid and do not produce this warning.

The analyzer also checks C# primary-constructor base calls. Constructor chains
produce a diagnostic at the unsafe base call, not at each `this(...)` call.
The rule does not prohibit Objective-C convenience initializers in general.

APL1000 is enabled by default for C# projects using the Apple SDK. It can be
suppressed using the standard `#pragma warning disable APL1000`, `.editorconfig`,
or `NoWarn` mechanisms, but suppression does not fix the native subclass.
