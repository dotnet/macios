# Authoring diagnostic documentation

These are the authoritative diagnostic sources for .NET for iOS, tvOS, macOS and Mac Catalyst. The layout follows [dotnet/android's diagnostic reference](https://github.com/dotnet/android/tree/main/Documentation/docs-mobile/messages): one lowercase Markdown filename per public code, YAML metadata including `f1_keywords`, and `Issue`/`Solution` sections.

## Add or change a diagnostic

1. Copy `docs/website/diagnostic-template.md` into this directory, replacing the code, message, date, edit link, category and logical diagnostic ID. Keep metadata strings double-quoted (JSON string escaping is valid YAML). Use one F1 keyword, matching the filename's uppercase code.
2. Document the cause and remedy; add an example where useful. Preserve historical information with its version/project applicability rather than describing retired Xamarin features as current .NET features.
3. Add an explicit mapping in `allocations.json` for a new English resource. Resource keys are not always public codes: shared MX resources can produce MT or MM, while runtime exceptions expose numeric codes. Inspect the emitting code rather than infer the prefix from the resource name.
4. Run `bash docs/update-diagnostic-docs.sh` and commit the pages, allocation mapping and regenerated indexes together. Run `bash docs/update-diagnostic-docs.sh check` to verify without changing files.

The checker also scans numeric emitters, including MSBuild logging extensions. The current `Xamarin.MacDev.Tasks` assembly emits MT codes on all platforms; the MM branch in `LoggingExtensions` applies to the older `Xamarin.Mac.Tasks` assembly. MSBuild resource names such as `E7138` and `W7144` are message identifiers, not public prefixes, and must not be substituted for the code passed to the logger.

Keep pages for emitted MSBuild diagnostics marked current, even when the legacy reference only described older project types. MT0012 and MT0158 had already acquired different MSBuild meanings before this migration; their pages explain the current message and preserve the retired message in a historical section.

The commands use the repository SDK under `builds/downloads/dotnet` when available, or `dotnet` on PATH. Set `DOTNET` to an executable path to override it. If the required SDK is missing, follow the repository build setup instructions.

`diagnostic_id` identifies a *meaning*, not a prefix. Pages sharing the same logical diagnostic use the same ID, even when the public prefixes differ. `diagnostic_status` is `current` or `historical`. Historical pages remain searchable and keep their original F1 keyword.

## Share explanations without a macro language

Use standard DocFX includes under `docs/includes/diagnostics`. Share text only when the explanation really applies to both tools/platforms; matching numbers do not prove matching meanings. Keep tool-specific instructions in the page wrapper or separate sections.

Every page has a direct macios edit link. Pages with shared explanations also link to the include source. GitHub shows the include directive rather than expanding it; the Microsoft Learn publishing preview renders the final explanation.

## Numeric allocations and historical codes

Do not reuse a historical number for a different meaning. If unrelated diagnostics conflict, prefer moving the newer diagnostic into an unused number. Check all prefixes and historical entries before allocating it.

`renumberings.json` reserves old codes and explains each reassignment. The migration moved conflicting binding diagnostics to BI1900–BI1910. The cache failures BI0003/BI0004 were introduced in 2023; several other overlaps predate this repository's original import, so their relative ages cannot be established here. For those, the tool allocations were retained and the binding allocations moved as a coherent group.

Update numeric emitters, resource keys, tests, expected logs, and any warning suppression/warnings-as-errors configuration. Resource designer files must be regenerated by the existing build, not edited manually. Do not edit generated translations; the localization workflow supplies the new resource IDs. Retain a historical page linking to the replacement. No compatibility alias is added for warning switches: users upgrading must update those numbers.

The legacy snapshot also preserves pre-existing retired allocations with different meanings. They are not revived or renumbered as if old released binaries could change.

## Generated files and synchronization

`index.md` and the three `docs/website/*-errors.md` compatibility indexes are generated. `legacy-indexes.json` records historical page/category headings and code anchors; do not delete entries when retiring a diagnostic. These compatibility indexes link to individual pages without downloading every explanation.

Run `bash docs/sync-mobile-docs.sh --docs-mobile-repo /path/to/docs-mobile` to copy the pages, shared includes and existing building-apps content to `docs/ios`. The template, authoring instructions and JSON manifests are not published. The script does not delete unrelated or retired destination files.

Use `--reverse` to import edits made in docs-mobile. The script checks incoming pages/includes and compares the incoming index with the index generated from those incoming pages **before copying**. An independent edit to the generated index is an error: move that edit to the individual page or reconcile it before syncing. Concurrent source edits still need manual reconciliation; this script is a copier, not a merge tool.

## Publication and IDE follow-up

The canonical URL pattern is `https://learn.microsoft.com/dotnet/ios/messages/mt0000` (substitute the lowercase public code).

The companion docs-mobile publication must add a navigation entry for `messages/index.md` to `docs/ios/TOC.yml`. Its existing DocFX configuration discovers message pages and expands includes while excluding include fragments from standalone articles.

Publish the canonical pages before updating old Xamarin pages or IDE links. Historical mtouch/mmp/binding URLs need their actual publishing owner's involvement; docs-mobile cannot automatically redirect a different site's paths. Preserve the legacy indexes and their code/category fragments at the old locations where publishing is still supported. A server cannot dispatch individual URL fragments because fragments are not sent with HTTP requests.

The existing [mtouch reference](https://learn.microsoft.com/previous-versions/xamarin/ios/troubleshooting/mtouch-errors) and [mmp reference](https://learn.microsoft.com/previous-versions/xamarin/mac/troubleshooting/mmp-errors) are archived Microsoft Learn content. Their published metadata identifies the `live` branch of `MicrosoftDocs/xamarin-docs-pr` as the source; the public [MicrosoftDocs/xamarin-docs](https://github.com/MicrosoftDocs/xamarin-docs) mirror is archived. Coordinate with that publishing owner rather than treating docs-mobile as the owner of those URLs. During migration verification, the original Xamarin routes redirected to the archive with their MT0000/MM0000 and category anchors intact, but the archived mtouch page did not contain MX8056. A live binding-error landing page was not established.

Verify old MT/MM/BI anchors, category anchors and MX8056, along with current direct pages in the publishing preview. Update current IDE consumers to the per-code URL pattern separately; existing consumers should continue reaching the anchor-bearing compatibility indexes. Do not claim legacy links or F1 navigation work end-to-end until publication and the relevant IDE have been verified.
